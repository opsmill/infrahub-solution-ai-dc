# Quickstart: Validate Multivendor Per-Vendor Configuration

End-to-end validation that maps to the spec's Success Criteria (SC-00x) and acceptance scenarios. Run against
a **freshly loaded** stack (re-vendoring renames interfaces, so in-place upgrade of an old stack is out of
scope — see spec Assumptions).

## Prerequisites

```bash
uv sync --all-packages
inv destroy && inv start      # fresh stack (clean graph)
inv load                      # schema → menu → objects (incl. new groups/templates/fabrics) → repository
```

Set an admin token for `infrahubctl` (see `dev/guides/`), then confirm the repository registered the three
per-vendor artifact definitions and no `startup_configuration` (the old one) remains.

## Scenario 1 — Vendor groups exist and are nested (SC-001, US1)

- In the UI (or GraphQL) confirm `cisco_devices`, `arista_devices`, `dell_devices` exist with
  `parent = devices`.
- Generate the fabrics (via the trigger pipeline or `infrahubctl generator …` for `generate-fabric`,
  `generate-pod`, `generate-rack`), then check each device is a member of `devices` **and** exactly one
  `{vendor}_devices` group.

**Expected**: no device in zero vendor groups; no device in two.

## Scenario 2 — Each fabric is single-vendor (SC-006, US2)

Query devices per fabric and check their `device_type.manufacturer.name`:

- **Fabric-A** → 100% `Cisco`
- **Fabric-B** → 100% `Arista`
- **Fabric-C** → 100% `Dell`

**Expected**: no vendor-less device anywhere; storage-rack leaves in Fabric-A are Cisco and in Fabric-B are
Arista (their new storage-leaf templates).

## Scenario 3 — Every template declares a device type (SC-005, US2)

```bash
# no template_name should lack a device_type after the change
grep -nE "template_name:|device_type:" objects/06_device_template.yml
```

**Expected**: the five generic templates are gone; every remaining `template_name` has a `device_type`.

## Scenario 4 — Exactly one config per device, from its vendor template (SC-002, US1)

- Render/inspect the startup-config artifact for a device in each fabric (`infrahubctl … artifact` or the UI
  artifact view).

**Expected**: each device produces exactly one startup-config artifact, generated by its vendor's transform
(`cisco_/arista_/dell_device_startup_config`).

## Scenario 5 — Per-vendor isolation (SC-003, US3)

- Make a visible edit to `transforms/templates/startup_config_dell.j2` only (e.g. add a comment line),
  reload the repository, and re-render configs.

**Expected**: Dell devices' configs change; Cisco and Arista device configs have a **zero-line diff**.

## Scenario 6 — Fail loudly on an unresolvable vendor (SC-004, US1)

- Temporarily point one rack's `leaf_switch_template` at a template with no `device_type` (or add a manufacturer
  with no vendor group) and run the rack generator.

**Expected**: generation fails with an error that **names the offending device**; no silent skip, no default
config. Revert the change afterward.

## Full-run gate (SC-007)

```bash
inv destroy && inv start && inv load
# then run the generator pipeline for all fabrics
```

**Expected**: a full load + generate of Fabrics A/B/C completes with **zero vendor-resolution errors**.
