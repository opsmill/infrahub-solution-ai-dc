# Critique: Kubernetes Clusters with Cilium BGP

**Feature**: `specs/004-kubernetes-cilium-bgp/`
**Date**: 2026-07-29
**Reviewed**: `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/*`, `quickstart.md`
**Verdict**: ⚠️ **PROCEED WITH UPDATES**

Out of scope for this critique, per the run's instructions: the PRD's already-agreed Implementation
and Testing Decisions — the module sketch, the no-new-generator boundary, the unit-tests-only

## Executive Summary

The spec and plan are unusually well-grounded: the external contracts were verified against primary
sources rather than assumed, and two inherited PRD claims were correctly falsified. The
one-cluster-config-per-member decision is justified by a *verified* Cilium constraint rather than a
guess. Test strategy is honest about what it does and does not cover.

One finding blocks: **the feature silently misbehaves once a second cluster exists**, and nothing in
the spec bounds it to one. This was confirmed empirically against the running stack, not inferred. It
is resolvable by scoping and documentation — no redesign — which is why the verdict is PROCEED WITH
UPDATES rather than RETHINK.

Three recommendations concern claims that are slightly stronger than the evidence supports (FR-006's
re-render, the empty-manifest withdrawal) or a foreseeable operator input that breaks SC-004 (node
selector validity). One recommendation guards against a future reader "fixing" a correct-but-odd-looking
query field and breaking Vidra.

### 3c — Alternative Approaches

The two live alternatives are both addressed with verified reasoning: per-node overrides (rejected —

### 3d — Edge Cases & User Experience

**P1 — 🎯 Must-Address — the feature breaks silently at more than one cluster.**

`CoreArtifact.name` is the artifact *definition's* `artifact_name`, identical across every target of
that definition. Verified against the running stack:

```text
CoreArtifact count: 3
   3 x 'Cabling Plan'
```

Three artifacts, three different fabric targets, **one shared name**. The cluster artifact will behave
identically: N clusters produce N `CoreArtifact` rows all named `Cilium BGP Manifest`.

Vidra's `InfrahubSync` selects an artifact **only** by `spec.source.artefactName`. There is no target,
cluster, or object selector in its CR. And Vidra's
`CreateArtifactsFromAPIResponse` iterates *every* returned edge, so it does not error on ambiguity — it
syncs all of them into the single configured destination namespace.

Consequence at N ≥ 2 clusters: every cluster receives every other cluster's `CiliumBGPClusterConfig`
documents. Partially mitigated — a foreign document's `nodeSelector` matches no node in the wrong
cluster, so it is inert rather than actively harmful, and the two shared documents collide by name
idempotently. But it is still N−1 clusters' worth of junk resources applied everywhere, and it becomes
genuinely harmful the moment a node-label value is reused across clusters.

Nothing in `spec.md` bounds the feature to a single cluster. `quickstart.md` step 7 even says "one
`CoreArtifact` edge per cluster" — observing the plurality without drawing the consequence.

*Suggestion*: bound v1 to one Cilium-consuming cluster per Infrahub branch, stated as an explicit
assumption and an out-of-scope item, with the mechanism (name-only selection) named so a reader
understands why. Add to `plan.md` Key Risks and to the artifact contract. The proper fix — per-cluster
artifact naming, or a Vidra-side target selector — belongs to whichever project owns it, not here.

**P2 — 💡 Recommendation — `node_selector` is not guaranteed to be a valid Kubernetes identifier.**

`node_selector` derives from `NetworkServerService.name`, which the schema constrains only as
`unique: true` free text. The rendered manifest uses that value in two places with stricter rules than
Infrahub enforces:

- `metadata.name` — must be an RFC 1123 subdomain (lowercase alphanumeric, `-`, `.`)
- `nodeSelector.matchLabels` value — ≤63 chars, alphanumeric with `-`, `_`, `.`

A service plausibly named `Cilium Worker 1` yields `metadata.name: Cilium Worker 1`, which the API
server rejects. That directly contradicts SC-004 ("applying with zero edits") and the failure surfaces
only at `kubectl apply` time, far from where the name was typed.

The repo's existing seeds are all already conformant, so this is latent rather than current.

*Suggestion*: record it as an explicit assumption and an edge case rather than adding validation —
adding a new fail-loud path would cut against the PRD's agreed "no new error types" and its decision
that ineligible members are omitted, not raised. Documenting the constraint on service naming is the
proportionate fix.

**P3 — 💡 Recommendation — the empty-manifest withdrawal is asserted but unverified.**

`spec.md` states "removing the last L3 member correctly withdraws all peering". Whether an empty
artifact body causes Vidra to *delete* previously-synced resources or to no-op (leaving stale
`CiliumBGPClusterConfig` objects in the cluster) is Vidra behaviour that was not verified — and could
not be, without running the operator.

If Vidra no-ops on an empty body, the last member's peering is never withdrawn and the spec's edge case
is simply false.

*Suggestion*: keep FR-005 exactly as it is (rendering zero documents is our side of the contract and is
correct either way), but downgrade the *withdrawal* claim from an asserted outcome to a stated
assumption about Vidra, and add it to `plan.md` Key Risks with the manual check to run.

### 3e — Success Measurement

**P4 — 💡 Recommendation — FR-006's "re-render" is half-verified, and the split isn't stated.**

FR-006 says the artifact "MUST re-render when a member is added, removed, or moved". The planned unit
tests render N vs N+1 vs moved-leaf fixtures — which verifies the manifest is a pure *function of* its
members. It does not verify that Infrahub actually re-renders on those changes; that depends on
artifact data-dependency tracking, which `research.md` R7 reasons about but nothing tests.

`quickstart.md` step 6 does cover the trigger manually, so the coverage exists — it just isn't labelled,
and a reader could mistake the unit tests for full FR-006 coverage.

*Suggestion*: state the split explicitly in the plan's testing context — function-of-members by unit
test, actual re-render by manual quickstart step 6.

## Engineering Lens Findings

### 4a — Architecture Soundness

The pure-module / thin-transform split is the right boundary and matches the established `servers.py`
and `overlay.py` convention, keeping all selection logic unit-testable with plain stubs. No circular
dependencies. The new top-level `queries/` directory is justified (the query backs neither a generator
nor a transform) and is picked up correctly, since `.infrahub.yml` registers queries by explicit
`file_path`.

**No findings.**

### 4b / 4d — Failure Modes, Performance & Scalability

Scale is not a factor (single-digit members on demo data), and the plan correctly identifies that the
property which *does* matter is checksum stability rather than throughput. Deterministic ordering is
specified with its own test.

**E1 — 💡 Recommendation — pin deterministic behaviour when a member has more than one cabled interface.**

`data-model.md` eligibility check 5 says "the server's cabling resolves to a leaf-port IP address". The
spec assumes one uplink per member (no multi-homing), so in practice there is one. But the module will
iterate `interfaces` and the *first match wins* — and "first" is query-order unless sorted. If a server
ever has a second cabled interface (a management port, or partial cleanup mid-move), `peerAddress` could
flip between renders, churning the checksum and making Vidra re-sync forever — the exact failure the
ordering requirement exists to prevent, reintroduced one level down.

*Suggestion*: specify that interface selection is deterministic (sort by interface name and take the
first eligible), not merely "the first found". One line in `data-model.md`; costs nothing.

### 4c — Security & Privacy

The manifest carries ASNs and point-to-point addresses — internal topology data, but no secrets, and no
more sensitive than the startup-config artifacts the repo already publishes. `authSecretRef` is out of
scope so no secret material is handled. Vidra authenticates with a bearer token it manages. No new
trust boundary, no compliance implication.

**No findings.**

### 4e — Testing Strategy

The table in `cilium-manifest-artifact.md` maps each check to a fixture, asserts on parsed structure
rather than text, and explicitly forbids whitespace and template-internal assertions. FR-009's check
("the existing suite passes with zero edits") is a genuinely good structural test of the design
constraint rather than a restatement of it.

Covered by **P4** above (labelling what the unit tests do and don't verify).

### 4f — Operational Readiness

**E2 — 💡 Recommendation — silent omission has no observability.**

Omitting ineligible members is a deliberate, agreed design decision and should stay. But it is the
feature's one non-fail-loud path, and `spec.md` concedes that a permanently broken member is
"detectable only as member count not matching document count" — i.e. only by a human manually counting.

The transform already has a logger available (the `InfrahubTransform` base provides one, as
`servers.py` helpers demonstrate). One log line per omitted member, naming the member and which
eligibility check it failed, converts an invisible failure into a diagnosable one at essentially zero
cost and with no change to rendered output.

*Suggestion*: add "log each omitted member and the reason" to the peering module's responsibilities.
This does not weaken the omit-don't-raise decision; it makes it debuggable.

Rollback: the schema changes are additive and every new field is optional or computed, so there is no
irreversible migration. Reverting means removing the artifact definition; deployed clusters keep their
last-synced state. Adequately handled.

### 4g — Dependencies & Integration Risks

**E3 — 💡 Recommendation — `storage_id { id }` looks like a bug and will get "fixed".**

The `ArtifactIDs` contract selects `storage_id { id }`. That looks wrong — `storage_id` is Infrahub's
storage identifier, so `{ value }` is the intuitive selection. Both were checked:

- Infrahub 1.11 introspection: `CoreArtifact.storage_id` is a `TextAttribute`, and `TextAttribute`
  exposes **both** `id` and `value`. So `{ id }` is *valid*, and returns the attribute node's UUID
  rather than the storage-id string.
- Vidra's `internal/adapter/infrahub/models.go` declares the field as a nested struct whose only member
  is `ID` with the JSON tag `id`, and assigns `StorageID: node.StorageID.ID`.

So `{ id }` is what Vidra parses, and the contract is **correct as written**. The risk is purely that a
future reader (or linter, or reviewer) will see `{ id }`, judge it a mistake, change it to `{ value }`,
and silently break every deployed consumer — Vidra would unmarshal an empty `StorageID` with no error.

*Suggestion*: annotate the line in `contracts/graphql-queries.md` with a do-not-change note recording
both verifications, so the reasoning survives the next reader.

Vidra itself: v1alpha1 API, single-maintainer project, and an external runtime dependency this repo
does not vendor. The plan already treats it as out-of-scope-to-operate, which is the right call. The
`artefactName` spelling quirk is captured.

## Cross-Lens Insights

**X1 = P1 — scope × integration correctness.** The multi-cluster finding is the one place where both
lenses converge, and it is why P1 is Must-Address rather than a recommendation. From the product side
it is an unstated scope boundary that a reader would not anticipate; from the engineering side it is a
concrete integration defect with a verified mechanism. Bounding the scope fixes both at once, and
costs nothing to implement — which is the signature of a finding worth acting on before tasks are
generated rather than after.

Notably, the two lenses **did not** converge on any simplification opportunity. That is a good sign
here: the design is already at close to minimum surface for what it delivers (one node kind, one
relationship, one computed attribute, one group, one module, one transform), and the critique found
nothing to cut.
